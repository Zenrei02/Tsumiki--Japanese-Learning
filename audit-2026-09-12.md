## 1. Needs a decision from Lloyd

### ① The only working undo for an account wipe is a hand-written SQL query — and the row that would fix it is scheduled *behind* the public beta

This is the one item I would not carry another week.

**What already happened, once, to Lloyd.** Session 25 Addendum 2: after the rename
deployed, his device's local keys were orphaned into the new namespace, he signed in, and
the empty device state **pushed over the account row** — version 7, `{}`, 2 bytes. It was
recovered only because `tsumiki_progress_archive` still held version 6 (812 bytes:
`engagement-v1`, `kanji-progress-v1`, `known-words-v1`), and Lloyd restored it by hand,
renaming the keys on the way in. Version 8, 836 bytes — 812 plus exactly 24, eight
characters of `tsumiki-` times three keys, so the values were byte-identical.

**The wipe itself was a decided cost.** Session 25: *"Lloyd took the expensive option at
every hazard: rename the export format outright, put every storage key in the tsumiki
namespace, migrate all the Supabase objects, and accept that his own device store
clears."* That is a choice, it is recorded, and this audit is not reopening it.

**What was not decided is that the recovery path is unreachable.** The tracker row
*"Surface `tsumiki_progress_archive` as restore-an-earlier-version"* is **Not started ·
Phase 2 — Beta · P1**. In the same phase, *"Open capped free tier to learner
communities"* is **P0**. As the rows stand, strangers arrive before the undo they would
need exists — and Session 25's own text says the archive *"has stopped being a
nice-to-have: it just performed the one job the backup file was load-bearing for, and a
learner cannot reach it."*

**And the learner's other escape hatch is gone.** Verified in `storage.js` **at the
deployed commit `f0e2fd6`**, not in the working tree:

```
111:    format: "tsumiki-progress",
139:  if (parsed?.format !== "tsumiki-progress" || !parsed.data) {
86-101: all thirteen KEYS carry the tsumiki- prefix
```

`git grep naoshi f0e2fd6 -- tsumiki-app/src` returns nothing, so there is no dual-accept
and no legacy-key read anywhere in the deployed app. Any progress file a tester exported
before Sep 6 now fails twice over: the format string is rejected outright
(*"That looks like a different kind of file."*), and even past that check every key in it
would be dropped by `importProgress`'s `KEYS.includes(k)` filter, yielding
*"That file had nothing in it."*

`RENAME-NOTES.md` §1 predicted this precisely and offered two ways out — leave the format
string alone, or accept both values on import for a release or two. Neither was taken.
Deliberately, per Session 25. **The file-restore path is therefore not a fallback for the
archive; there is currently no learner-reachable undo at all.**

**The mechanism is worth recording, because it generalises past this rename.** I checked
whether the merge guard is at fault. It is not — `mergeProgress` is sound:

```js
if (lEmpty) { merged[k] = r; pulled.push(k); continue; }   // sync.js:145
```

An empty local pulls remote, so a genuinely fresh device does **not** overwrite an
account. `test-progress-sync.py` passes. The wipe happened because `exportProgress()` and
`pushRemote()` both filter through `KEYS`, and after a key-namespace change that filter
emptied **both** inputs before the merge ever saw them. **The guard is sound and sits
downstream of a filter that can silently empty its own inputs.** That is the same shape as
Session 25's `netlify.toml` finding — the rule was true, the precondition for it silently
was not.

**Decisions wanted:**

- (a) Move the archive-surfacing row ahead of *Open capped free tier*, or record
  explicitly that the beta opens without an undo.
- (b) Approve a `pushRemote` guard: refuse to upsert an empty `clean` map over a
  non-empty remote row. One condition, and it makes the next namespace change survivable.
  Proposed, not applied — see §3.
- (c) Optional and cheap: accept `"naoshi-progress"` on import as well. It costs one
  `||` and it un-bricks every backup file already on a tester's disk.

## 6. What I could not check, and how to check it

Stated with the method attached, so it is retried cheaply rather than becoming a wall.

- **Blast radius of the account wipe — how many accounts exist and what their rows hold.**
  A read-only `SELECT` against `tsumiki_progress` was refused by the tool-permission layer
  (`AbortError: Tool permission stream closed`) — this run is unattended, so no one could
  approve it. **One query answers it** in an interactive session:
  ```sql
  select user_id, version, updated_at,
         (select count(*) from jsonb_object_keys(data) k) as n_keys
  from tsumiki_progress order by updated_at desc nulls last;
  ```
  Until then, §1① is argued from mechanism and from one observed occurrence, not from a
  count. Session 25 describes the account store as the one with real accumulated use in
  it, which suggests the population is small.

- **A read of the live production bytes.** The browser pane needs per-site approval and
  nobody was present to give it; `web_fetch` refused the URL as outside its provenance
  set. **So the production evidence in §1① and §2 is: the Netlify API's deploy record
  (`commit_ref`, `published_at`, `state: ready`) plus git at that ref.** Two channels, and
  the API one timestamps the build — but neither is a read of the served JavaScript. State
  which of the two you have when quoting this. `https://tsumiki-jp.netlify.app/?cb=…`
  settles it in one call from an interactive session.
