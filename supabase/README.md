# The checker backend

One Edge Function, `check`, plus the table behind the daily cap. It holds the
Anthropic API key so the browser never does.

Why Supabase rather than Netlify Functions: `backend-host-decision-v1.md`. The
short version is that a check takes ~17s median and ~63s at the observed
maximum, Netlify's synchronous ceiling is 60s and not configurable, and
Supabase's is 150s on the free plan.

```
supabase/
  functions/
    check/spans.ts          span placement + fallback (tested by test-spans.mjs)
    check/stream-extract.ts SSE + incremental JSON decoding for the streaming
                            path (tested by test-stream-extract.mjs)
    check/index.ts          the handler — hand-maintained
    check/_prompt.ts        GENERATED by build-checker-endpoint.py, do not edit
  migrations/
    20260815000000_check_usage.sql
```

## One-time setup

**0. Getting the CLI.** You do not have to install anything. `npx` runs it on
demand, and this repo already has Node for the Vite build:

```
npx supabase@latest --version
```

Needs Node 20 or newer. Homebrew (`brew install supabase/tap/supabase`) gives
you a global `supabase` command instead, but it is optional — and
`npm install -g supabase` is **explicitly unsupported**, so don't reach for it
when brew misbehaves.

**Docker is not required for any of this.** It is only needed for
`supabase start`, which runs the whole stack locally — we are deploying to the
hosted project instead.

Every command below is written bare (`supabase …`). If you are using npx,
prefix each one with `npx supabase@latest` instead.

**1. Log in and link** (from the repo root, where the `supabase/` folder lives):

```
supabase login
supabase link --project-ref llkazgmhsuonhwrubwjw
```

⚠️ **The code `supabase login` prints is a MATCH code, not something you type
back in.** The CLI shows it, opens a browser, and the browser shows the same
code so you can confirm they are the same session. You approve in the browser
and the terminal continues by itself. There is no CLI prompt waiting for it —
looking for one is the trap, and it cost Lloyd a detour on Aug 15 2026.

**If the browser never opens, or the terminal just sits there, skip login.**
The CLI reads `SUPABASE_ACCESS_TOKEN` instead, and the docs explicitly offer
this as the alternative. Create a token at
[supabase.com/dashboard/account/tokens](https://supabase.com/dashboard/account/tokens),
then:

```
read -rs SUPABASE_ACCESS_TOKEN && export SUPABASE_ACCESS_TOKEN
```

`read -rs` prompts with echo off, so the token never appears on screen and
never enters shell history — unlike `export SUPABASE_ACCESS_TOKEN=sb_pat_…`,
which does both. It lasts for that terminal window only, which is the right
lifetime: run the rest of the setup in the same window.

**This token is a real secret** — it is full account access, not a publishable
key. It does not belong in a chat, a commit, or the tracker.

If `link` complains about a missing config, run `supabase init` first — it only
adds `supabase/config.toml` and leaves `migrations/` and `functions/` alone.

**2. Apply the migration.** ✅ **Already done** — applied Aug 15 2026 against
project `llkazgmhsuonhwrubwjw`, recorded as version `20260814180650`, and the
local filename was renamed to match. So this is now a no-op and should print
"Remote database is up to date":

```
supabase db push
```

If it ever offers to apply `check_usage` again, stop and look — the local file
and the remote record have diverged.

**3. Set the secrets.** Do this yourself. None of these values should be pasted
into a chat, an artifact, a commit, or the tracker.

**Set `ANTHROPIC_API_KEY` in the dashboard, not the CLI** — Edge Functions →
Secrets. A `supabase secrets set` with the key inline lands in your shell
history, which is a file that gets backed up and grepped. The dashboard form
does not.

The salt has no such problem, because it is generated in place and never
appears as a literal:

```
supabase secrets set TSUMIKI_CAP_SALT="$(openssl rand -hex 32)"
```

⚠️ **Set the salt once and leave it.** Changing it re-keys every subject hash,
so every learner's counter silently resets to zero — the cap stops bounding
anything for a day and nothing reports it.

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are injected automatically —
you do not set those.

Optional, all with working defaults:

| Secret | Default | What it does |
|---|---|---|
| `TSUMIKI_MODEL` | `claude-sonnet-5` | Which model answers. Change it when the bake-off returns a verdict — no redeploy of anything else needed. |
| `TSUMIKI_DAILY_CAP` | `10` | Checks per client per day. This is the cost bound. |
| `TSUMIKI_MAX_CHARS` | `600` | Longest text accepted. Caps the per-call cost. |
| `TSUMIKI_ALLOWED_ORIGIN` | `*` | Set to the deployed site's origin before real traffic. |

**4. Deploy:**

```
supabase functions deploy check --no-verify-jwt
```

**Why `--no-verify-jwt`.** The default requires every caller to send a valid
JWT. For a signed-in app that is right. This endpoint is the opposite: an
anonymous public checker, so the only token the browser could send is the
publishable anon key — which ships inside the JS bundle and is readable by
anyone who opens devtools. It would be a lock with the key taped to it, in
exchange for an extra env var and a 401 the day someone forgets it.

The controls that actually do the work here are server-side and already built:
the daily cap (a real cost bound, enforced in Postgres) and
`TSUMIKI_ALLOWED_ORIGIN`. **Narrow that origin from `*` to the deployed site
before the URL is public** — with it wide open, anyone can spend your API
budget up to ten checks per IP per day.

If accounts land and checks become a signed-in feature, drop the flag and send
the user's session token. That is a deliberate later change, not a default to
drift into.

Deploying costs no Netlify credits and is not subject to the one-push-per-session
rule. Iterate freely here.

## Checking it works

Deployed with `--no-verify-jwt`, so no auth header is needed:

```
curl -i -X POST "https://llkazgmhsuonhwrubwjw.supabase.co/functions/v1/check" \
  -H "content-type: application/json" \
  -d '{"text":"私は毎日私の犬と散歩します。","context":"casual"}'
```

That sentence is deliberately chosen: it carries the pronoun-overuse pattern the
prompt's L1-interference watchlist names first, so a healthy response contains
at least one issue with `"located": true`. A response with `"issues": []` on it
is a signal that the prompt did not arrive — check `_prompt.ts` was generated.

**Verify the artifact, not the log.** Twice in this project a success message
has hidden a failure (the trashed-forms patch, the B7/B8 rebuild). A deploy that
prints "Deployed" only tells you a bundle was uploaded. Curl the endpoint.

## Reading the response

```jsonc
{
  "schema": "naoshi-4",       // which prompt produced this
  "model":  "claude-sonnet-5",// as ANSWERED, not as requested
  "verdict": "FIX",           // strongest tier wins, same as the harness
  "overall": { "natural_score": 3, "summary": "..." },
  "issues": [
    { "span": "私の", "start": 4, "end": 6, "located": true, ... }
  ],
  "model_rewrite": "...",
  "readings": [["毎日","まいにち"]],
  "spans": { "total": 2, "located": 1, "notFound": 1, "overlapped": 0 },
  "cap":   { "used": 3, "limit": 10 }
}
```

`located: false` means the model returned a span that is not in the input
verbatim. The issue is still returned — it may be good advice — but it must be
rendered as a card with **no highlight**. Highlighting it would attach the
explanation to the wrong characters, and the learner cannot catch that.

`spans.notFound` climbing across real traffic is a prompt regression, not a
rendering bug. It is logged server-side for that reason.

## The streaming path (`"stream": true`)

Opt-in per request. Everything above is unchanged and remains the default.

```
curl -N -X POST "https://llkazgmhsuonhwrubwjw.supabase.co/functions/v1/check" \
  -H "content-type: application/json" \
  -d '{"text":"私は毎日私の犬と散歩します。","context":"casual","stream":true}'
```

`-N` disables curl's own buffering; without it the events arrive in one lump and
it looks like nothing was streamed.

Total time does not improve — the model takes as long as it takes. What improves
is time-to-first-useful-thing: `overall` lands early, then issues one at a time.

```
event: overall   data: {"natural_score":3,"summary":"..."}
event: issue     data: {"span":"私の","start":4,"end":6,"located":true,...}
event: rewrite   data: {"model_rewrite":"..."}
event: readings  data: {"readings":[["毎日","まいにち"]]}
event: done      data: {"schema":"naoshi-4","model":"...","verdict":"FIX",
                        "spans":{...},"cap":{...},"usage":{...}}
event: error     data: {"error":"upstream-timeout"}
```

**We emit our own events; Anthropic's stream is never proxied.** Span
verification has to stay server-side — the guarantee is that every `start`/`end`
was checked character-for-character against the submitted text, and forwarding
raw model output would move that into the browser or drop it. Thinking deltas
are dropped at the same boundary.

⚠️ **A stream that ends without `done` is a FAILURE, not a short result.** Once
headers are sent the status is fixed at 200, so late errors arrive in-band as
`event: error`. A client that treats a dropped connection as "no issues found"
would produce exactly the invisible failure this checker exists to prevent, so
`done` is only ever sent when the model's JSON object actually closed.

`readings` arrives last, because the prompt fixes the key order and reordering it
would change what the bake-off measured. Render text without ruby and apply
furigana when `readings` lands — that is a client concern and is not built yet.

**The buffered path stays** because `bakeoff-harness.py` must keep making the
request that was measured, because it is the fallback if streaming misbehaves in
a browser we cannot test, and because it is far easier to curl. The two requests
are built by one function in `index.ts`, differing only by `stream: true`, so
"streaming changes delivery and not generation" is checkable rather than a
claim.

Chunk boundaries are where streaming parsers die, and in Japanese text a network
chunk splits a multi-byte character constantly. `test-stream-extract.mjs` runs
the same payload split at **every character position and every byte position**
and asserts the output never changes. Run it after touching either decoder:

```
node test-stream-extract.mjs
```

## Things that will bite

- **`_prompt.ts` is generated.** Editing `SYSTEM_PROMPT` in
  `tsumiki-prototype.jsx` and redeploying without re-running
  `python3 build-checker-endpoint.py` ships the old prompt. The generator
  refuses to write a prompt under 2,000 chars or one missing the JSON contract,
  so a broken extraction fails loudly rather than silently.

- **The four Claude 5 API facts** are implemented in `index.ts` and commented
  there: no `temperature`/`top_p`/`top_k`; thinking on by default and billed as
  output inside `max_tokens` (hence 8000); no assistant prefill; thinking blocks
  precede text blocks so `content[0]` is unsafe. Any request code written before
  2026 gets all four wrong.

- **The cap fails open.** If Postgres is unreachable the function logs
  `CAP DISABLED` and serves the check anyway — a database blip should degrade
  the cap, not take the product down. Grep the logs for `CAP DISABLED` before
  concluding spend is bounded.

- **The bake-off measured free-text JSON**, which is what this endpoint parses.
  The tracker also records the docs' recommendation to use a tool `input_schema`
  for JSON output, which is more robust against truncation. That is a real
  upgrade, but switching before the verdict lands would mean shipping a request
  shape the bake-off never measured. Decide it deliberately, afterwards.
